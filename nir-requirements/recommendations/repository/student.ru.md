# Репозиторий и работа с кодом — памятка студенту

Памятка описывает, как вести работу, чтобы руководитель мог запустить репозиторий из чистого клона, pull request фиксировали сделанное, решения записывались в журнал, а эксперименты — в MLflow. Следуйте ей с первой недели: по списку в конце руководитель проверяет работу на каждой контрольной точке.

## Термины

| Термин | Пояснение | Что это значит для вас |
|---|---|---|
| Pull request (PR), Draft, Ready for review | PR предлагает влить изменения из ветки в `main`; к нему прилагаются описание и обсуждение на ревью. Draft помечает незаконченную работу; Ready for review запрашивает ревью. | Draft нельзя смержить, и он не запрашивает ревью. Снимайте Draft только когда работа готова. |
| CODEOWNERS | Файл `.github/CODEOWNERS` закрепляет за путями в репозитории ревьюеров; когда PR переходит в Ready for review, GitHub запрашивает у них ревью. | Одна строка `* @<руководитель>` делает руководителя ревьюером каждого PR. Работает только после мержа файла в `main`. |
| Ruleset, защита ветки | Настройки репозитория, которые запрещают прямые push в `main` и требуют PR, аппрув, закрытые обсуждения или зелёные проверки. | Бесплатно на публичном репозитории; на приватном только на платном тарифе. Без них правила держатся на договорённости. |
| ADR, журнал решений, статусы | Запись архитектурного решения — один файл на решение: контекст, варианты, решение, последствия. Папка с записями — журнал решений. Статусы: proposed, accepted, rejected, superseded. | Принятую запись не правят; чтобы изменить решение, создайте новую запись, которая заменит старую. |
| Tracking server, backend store, artifact store | Части MLflow: сервер принимает запуски; backend store хранит параметры, метрики и теги в базе данных; artifact store хранит файлы, модели, графики и конфиги, например в S3-совместимом хранилище вроде MinIO. | Локально файл `mlflow.db` — backend store, а артефакты ложатся в папку; на общем сервере лаборатории настроены все три. |
| Эксперимент, запуск, параметр, метрика, артефакт, тег | Понятия MLflow: эксперимент объединяет запуски; запуск — одно выполнение с параметрами (входные значения), метриками (числа, которые меняются по ходу выполнения), артефактами (файлы) и тегами (метки, включая коммит). | Для каждого числа в вашей таблице результатов должен быть указан запуск, в котором оно получено. |
| `.env`, `.env.example`, переменная окружения | Настройки, которые на разных машинах разные (пути, адреса, ключи), хранятся в переменных окружения. `.env` хранит их локально и внесён в `.gitignore`; `.env.example` перечисляет ключи с заглушками и лежит в репозитории. | Руководитель копирует `.env.example` в `.env`, заполняет и запускает проект. |
| Repository secret, environment secret | Зашифрованные значения для GitHub Actions. Repository secrets может создать collaborator; environment secrets — только владелец. | Учётные данные для CI храните только там, а не в файле workflow и не в PR. |
| Хук pre-commit, хук VCS, хук агента | Словом «хук» называют три разных механизма: pre-commit запускает проверки перед коммитом и настраивается в `.pre-commit-config.yaml`; обычный хук VCS — скрипт в `.git/hooks`; хук агента запускает команду на определённом шаге работы LLM-ассистента. | Памятка использует pre-commit и хук агента; оба запускают один и тот же `make check`. |
| Lock-файл (`uv.lock`) | Файл, в котором зафиксированы точные версии всех зависимостей проекта. | Коммитьте его. CI ставит окружение из него командой `uv sync --locked`, поэтому запуск, привязанный к коммиту, можно повторить. |
| Harness, LLM harness | Среда, в которой работает LLM-ассистент: его файлы инструкций, разрешения, хуки и проверки, которые они запускают. | Harness запускает `make check` после правок, поэтому ассистент не может оставить репозиторий с упавшими проверками. Подробнее о нём — в [памятке об агентных артефактах](../agents/student.ru.md). |

## Репозиторий и доступ

- Создайте репозиторий в своём личном аккаунте. Переносите его в организацию лаборатории только тогда, когда код понадобится в проекте лаборатории.
- Руководитель — collaborator с правом write и Admin вашего GitHub Project. Других ролей у личного репозитория нет, поэтому то, что может сделать только владелец, делаете вы по просьбе руководителя: видимость, rulesets, мерж CODEOWNERS и шаблона PR, environment secrets, перенос.
- Видимость выбираете вы. Рекомендуем публичный, если этому не мешают ограничения на данные или интеллектуальную собственность. От видимости зависит, какие правила платформа может обеспечить сама:

| Что обеспечивает платформа | Публичный, Free | Приватный, Free |
|---|---|---|
| Rulesets: обязательный PR, аппрув, закрытые обсуждения, зелёные проверки | да | нет |
| Ревью от code owners | да | нет |
| Secret scanning и push protection | да | нет |
| Draft PR, запрос ревью через CODEOWNERS, минуты Actions | да | да, 2 000 минут в месяц |

- На приватном репозитории те же правила держатся на договорённости; единственный автоматический барьер там — CI.
- Держите полный локальный клон и второй remote (вузовский GitLab или другой Git-хостинг): доступ к платформе бывает нестабильным, а руководитель запускает именно чистый клон.

## Структура и что не попадает в репозиторий

```
README.md  .env.example  pyproject.toml  uv.lock  Makefile
.github/          pull_request_template.md, CODEOWNERS, workflows/
src/<package>/    код, который импортируется и тестируется
notebooks/        исследовательский анализ; вывод ячеек можно оставить как отчёт о результате
docs/adr/         журнал решений
configs/          конфиги экспериментов
data/             в .gitignore; допустим разве что крошечный образец с пометкой
results/          таблицы и рисунки, экспортированные из кода
```

- README — вход в проект: назначение, `cp .env.example .env`, `uv sync`, `make check`, команда запуска одного эксперимента, где лежат данные, ссылки на журнал решений и Project. Всё должно работать из чистого клона.
- Коммитьте `uv.lock`; CI ставит окружение через `uv sync --locked`; перед открытием PR запускайте `uv lock --check`.
- Никогда не коммитьте секреты и `.env`, сырые данные, веса моделей, файлы больше нескольких десятков МБ, сгенерированные логи. Данные и артефакты хранятся в MLflow и MinIO или в хранилище кластера; в README напишите, как их получить. GitHub предупреждает о файлах больше 50 МБ и отклоняет файлы больше 100 МБ.
- Конфигурация хранится в переменных окружения. `.env` лежит только локально и внесён в `.gitignore`; в `.env.example`, который хранится в репозитории, перечислены все ключи, у каждого есть заглушка и однострочный комментарий. Загружайте конфигурацию через python-dotenv или типизированный класс настроек, который сразу падает, если ключа нет.
- Подключите хуки pre-commit с первого дня: gitleaks и detect-private-key ловят секреты, check-added-large-files — большие файлы с данными, плюс `make check`. В каждом новом клоне нужно выполнить `pre-commit install`; напишите об этом в README.
- Ключ, попавший в историю, скомпрометирован: сначала отзовите его и выпустите новый, затем решите с руководителем, переписывать ли историю. Если удалить файл новым коммитом, ключ всё равно останется в истории.
- Используйте один seed: читайте его из окружения, задавайте для `random`, NumPy и фреймворка и логируйте как параметр запуска. Побитовое совпадение между версиями библиотек и устройствами не гарантировано; гарантировать вы можете только одинаковые seed и lock-файл.
- Ноутбуки храните в `notebooks/`, вывод ячеек в них можно оставить как отчёт о результате; код, который понадобится повторно, переносите в `src/`.

## Ветки и коммиты

- Имя ветки: `<тип>/<короткое-описание>` строчными буквами через дефис. Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, плюс `exp` для серии экспериментов. С того же типа начинается заголовок PR: `feat: ...`.
- Одна ветка на одно изменение; она живёт дни, а не недели. Коммитьте и пушьте в конце каждой рабочей сессии, чтобы по истории было видно, что работа шла равномерно, неделя за неделей.
- Никогда не переписывайте запушенную историю `main`. Мержите PR через squash and merge; тогда заголовок PR станет сообщением коммита в `main`.
- Мелкие правки могут идти в `main` напрямую по договорённости с руководителем; хуки pre-commit срабатывают и на них.
- Правила оформления сообщений коммитов необязательны, но полезны: см. [Сообщения коммитов](commit-messages.ru.md).

## Pull request

Вся работа проходит через pull request: он и есть запись того, что сделано и почему. Одна ветка на одно изменение, один PR на ветку.

Поля PR:

- заголовок в стиле ветки: `feat: короткое описание`;
- **План**: при открытии PR сами напишите три-пять строк о том, что собираетесь сделать;
- **Сделано**: перед снятием Draft попросите LLM-ассистента составить по диффу краткое описание проделанной работы; План и строку `Closes #N` не меняйте;
- **Как воспроизвести**: что должен запустить ревьюер, чтобы получить результат: команда и её конфиг, источник данных, запуск MLflow с метриками;
- assignee: вы; reviewer: руководитель, его подставит CODEOWNERS при снятии Draft;
- label `enhancement` для новой функциональности;
- Draft, пока работа не готова. Draft нельзя смержить, и он не запрашивает ревью.

Положите шаблон с этими полями в `.github/pull_request_template.md`: тогда PR никогда не откроется пустым.

Цикл ревью:

1. Руководитель читает PR и оставляет все комментарии за один проход.
2. Вы правите отдельными коммитами, без squash и rebase во время ревью, и отвечаете под каждым обсуждением: что изменили и в каком коммите.
3. Повторно запрашиваете ревью кнопкой Re-request review.
4. Обсуждения закрывает руководитель. GitHub позволяет закрыть их и автору, поэтому правило держится на договорённости.

Сроки ответа обсудите с руководителем. Пока ждёте, начинайте следующую ветку от текущей; не копите работу всего семестра в одном PR.

Несогласие с замечанием: сначала уточните, правильно ли поняли; спорьте фактами и сравнением плюсов и минусов, вкусовые предпочтения аргументом не считаются; предложите два-три варианта; архитектурное решение оформите в ADR.

## Решения

Решения хранятся в `docs/adr/`, по одному файлу на решение: `NNNN-короткое-название.md`. Номер четырёхзначный и сквозной, его никогда не используют повторно; в названии — проблема и выбранное решение. Оформляйте файл по минимальному шаблону MADR с фронтматтером:

```
---
status: proposed | accepted | rejected | superseded by ADR-NNNN
date: 2026-09-24
decision-makers: <студент>
consulted: <руководитель>
---
# <Проблема и выбранное решение>
## Контекст и постановка проблемы
## Рассмотренные варианты
## Итог решения
### Последствия
## Плюсы и минусы вариантов    <- обязательно, когда отвергнут вариант, предложенный руководителем
```

- Запись составляет ваш LLM-ассистент, а не вы вручную: в момент решения попросите ассистента составить её по обсуждению, ветке PR и коду, затем проверьте её так же, как проверяете код.
- Что заслуживает записи: структура репозитория и поток данных; библиотека, фреймворк или инструмент вроде трекера, хранилища или LLM-шлюза; интерфейс или контракт данных; бейзлайн, главная метрика, датасет и его разбиение; направление, закрытое отрицательным результатом. Отдельный запуск с другими гиперпараметрами фиксируется в MLflow, записи в журнале для него не нужно.
- Запись создаётся в ветке фичи со статусом proposed, проходит ревью в PR наравне с кодом и получает статус accepted в том же PR до мержа. Отклонённую запись тоже мержат, указав причину отказа. Принятую запись не правят; чтобы изменить решение, создайте новую запись, которая заменит старую, и поставьте ссылки в обе стороны.
- Запись ссылается на эксперимент или запуск MLflow, который привёл к этому решению.

## Эксперименты и воспроизводимость

- Каждый эксперимент записывается в MLflow. По умолчанию — локальная база: `MLFLOW_TRACKING_URI=sqlite:///mlflow.db` в `.env`, папки `mlruns/` и `mlartifacts/` в игноре. Если вы коммитите `mlflow.db`, чтобы руководитель мог открыть его командой `mlflow ui --backend-store-uri sqlite:///mlflow.db`, соблюдайте условия: в базу пишет только один автор, перед коммитом выполняется `mlflow gc`, файл меньше 50 МБ, коммит сделан в той ветке PR, где получены запуски; при конфликте слияния оставьте одну из версий и перезапустите эксперименты. Документация MLflow эту практику не описывает.
- В первую неделю спросите руководителя, есть ли у лаборатории общий tracking server. Если есть, переключите клиент на него: `MLFLOW_TRACKING_URI=https://<сервер>`, `MLFLOW_EXPERIMENT_NAME`, а для S3-совместимого хранилища артефактов `MLFLOW_S3_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` в `.env`; в `.env.example` перечислите их без значений. Например, в нашей лаборатории сервер и MinIO развёрнуты на кластере.
- Имена: эксперимент `<репозиторий>` или `<репозиторий>/<задача>`; имя запуска `<ветка>-<короткое-описание>`; всегда вызывайте `mlflow.set_experiment`.
- Обязательные теги (их набор один раз согласуйте с руководителем): `stage` (baseline, ablation, final), `dataset`, `model_family`, `pr` (номер). В заметках к запуску напишите один абзац с описанием.
- Запускайте эксперименты скриптами из рабочей копии репозитория (`uv run python -m <package>.train`) и только после коммита: тогда MLflow сам запишет коммит. У запусков из ноутбуков тега с коммитом нет.
- Минимум логирования: вызовите `mlflow.autolog()` перед обучением, сохраните конфиг как артефакт, а итоговую таблицу метрик залогируйте явно.
- Каждая строка таблицы результатов содержит коммит, путь к конфигу, seed, id запуска и метрики. Таблица хранится в `results/` или в PR; в ВКР ссылайтесь на неё.

## Автоматические проверки

- Одна цель `make check` запускает всё: линт и форматирование ruff, pytest хотя бы с одним smoke-тестом, который прогоняет главный пайплайн на крошечном входе за секунды.
- Эту цель вызывают три механизма: pre-commit на вашей машине, CI на каждом PR и хук агента после правок ассистента. Добавьте команду в файл инструкций, который читает ассистент; готовые настройки для всех трёх мест есть в [памятке об агентных артефактах](../agents/student.ru.md#одна-проверка-для-агента-pre-commit-и-ci).
- CI на PR добавляет то, что машина проверяет лучше человека: имя ветки и заголовок PR по списку типов, gitleaks, большие файлы, `uv sync --locked`. Задания, которым нужны учётные данные лаборатории, необязательны и пропускаются, если секрет не задан.
- Никогда не коммитьте с `--no-verify`; если проверка упала, устраните причину.

## Минимальный ожидаемый результат

К каждой контрольной точке покажите руководителю:

1. Репозиторий запускается из чистого клона командами из README.
2. PR, смерженные за этот период; в каждом заполнены поля «План», «Сделано» и «Как воспроизвести».
3. Записи в `docs/adr/` по принятым решениям.
4. Запуски MLflow на коммитах этих PR с обязательными тегами.
5. Зелёный CI на `main`; в истории нет секретов и данных.
