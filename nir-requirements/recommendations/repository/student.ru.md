# Репозиторий и работа с кодом — памятка студенту

Памятка ведёт к репозиторию, который руководитель запускает из чистого клона, к pull request как записи вашей работы, к журналу решений и к экспериментам, записанным в MLflow. Применяйте с первой недели; список в конце и есть то, что руководитель проверяет на каждой контрольной точке.

## Термины

| Термин | Пояснение | Что это значит для вас |
|---|---|---|
| Pull request (PR), Draft, Ready for review | PR предлагает изменение из ветки в `main`, с описанием и обсуждением ревью. Draft помечает незаконченную работу; Ready for review запрашивает ревьюера. | Draft нельзя смержить, и он не запрашивает ревью. Снимайте Draft только когда работа готова. |
| CODEOWNERS | Файл `.github/CODEOWNERS` сопоставляет пути ревьюерам; GitHub запрашивает их, когда PR становится Ready for review. | Одна строка `* @<руководитель>` делает руководителя ревьюером каждого PR. Работает только после мержа файла в `main`. |
| Ruleset, защита ветки | Настройки репозитория, которые запрещают прямые push в `main` и требуют PR, аппрув, закрытые обсуждения или зелёные проверки. | Бесплатно на публичном репозитории; на приватном только на платном тарифе. Без них правила держатся на договорённости. |
| ADR, журнал решений, статусы | Запись архитектурного решения — один файл на решение: контекст, варианты, решение, последствия. Папка с записями — журнал решений. Статусы: proposed, accepted, rejected, superseded. | Принятая запись никогда не правится; изменение — новая запись, которая заменяет старую. |
| Tracking server, backend store, artifact store | Части MLflow: сервер принимает запуски; backend store хранит параметры, метрики и теги в базе данных; artifact store хранит файлы, модели, графики и конфиги, например в S3-совместимом хранилище вроде MinIO. | Локально файл `mlflow.db` — backend store, а артефакты ложатся в папку; на общем сервере лаборатории настроены все три. |
| Эксперимент, запуск, параметр, метрика, артефакт, тег | Словарь MLflow: эксперимент группирует запуски; запуск — одно выполнение с параметрами (входы), метриками (числа во времени), артефактами (файлы) и тегами (метки, включая коммит). | Каждое число в вашей таблице результатов указывает на запуск. |
| `.env`, `.env.example`, переменная окружения | Конфигурация, которая различается между машинами (пути, адреса, ключи), живёт в переменных окружения. `.env` хранит их локально и игнорируется; `.env.example` перечисляет ключи с заглушками и коммитится. | Руководитель копирует `.env.example` в `.env`, заполняет и запускает проект. |
| Repository secret, environment secret | Зашифрованные значения для GitHub Actions. Repository secrets может создать collaborator; environment secrets — только владелец. | Учётные данные, нужные CI, идут туда и никогда в файл workflow или в PR. |
| Хук pre-commit, хук VCS, хук агента | Три механизма делят одно слово: pre-commit запускает проверки перед коммитом, настраивается в `.pre-commit-config.yaml`; голый хук VCS — скрипт в `.git/hooks`; хук агента запускает команду на шаге работы LLM-ассистента. | Памятка использует pre-commit и хук агента; оба запускают один и тот же `make check`. |
| Lock-файл (`uv.lock`) | Точная версия каждой зависимости, разрешённая для проекта. | Коммитьте его. CI ставит окружение из него командой `uv sync --locked`, поэтому запуск, привязанный к коммиту, можно повторить. |
| Harness, LLM harness | Среда, в которой работает LLM-ассистент: его файлы инструкций, разрешения, хуки и проверки, которые они запускают. | Harness запускает `make check` после правок, поэтому ассистент не может оставить репозиторий красным. Отдельная памятка об агентных артефактах описывает его. |

## Репозиторий и доступ

- Репозиторий живёт в вашем личном аккаунте. Переносите его в организацию лаборатории только когда код нужен в проекте лаборатории.
- Руководитель — collaborator с правом write и Admin вашего GitHub Project. Других ролей у личного репозитория нет, поэтому действия только для владельца остаются за вами, и вы делаете их по просьбе: видимость, rulesets, мерж CODEOWNERS и шаблона PR, environment secrets, перенос.
- Видимость выбираете вы. Рекомендация: публичный, пока данные или интеллектуальная собственность не запрещают. Видимость решает, что платформа может принудить:

| Принуждает платформа | Публичный, Free | Приватный, Free |
|---|---|---|
| Rulesets: обязательный PR, аппрув, закрытые обсуждения, зелёные проверки | да | нет |
| Ревью от code owners | да | нет |
| Secret scanning и push protection | да | нет |
| Draft PR, запрос ревью через CODEOWNERS, минуты Actions | да | да, 2 000 минут в месяц |

- На приватном репозитории те же правила держатся на договорённости; единственный автоматический барьер там — CI.
- Держите полный локальный клон и второй remote, вузовский GitLab или другой форж: доступ к платформе бывает нестабильным, а руководитель запускает именно чистый клон.

## Структура и что не попадает в репозиторий

```
README.md  .env.example  pyproject.toml  uv.lock  Makefile
.github/          pull_request_template.md, CODEOWNERS, workflows/
src/<package>/    код, который импортируется и тестируется
notebooks/        разведка; выводы могут остаться как отчёт о результате
docs/adr/         журнал решений
configs/          конфиги экспериментов
data/             в игноре; самое большее крошечный помеченный образец
results/          таблицы и рисунки, экспортированные из кода
```

- README — вход в проект: назначение, `cp .env.example .env`, `uv sync`, `make check`, команда запуска одного эксперимента, где лежат данные, ссылки на журнал решений и Project. Всё должно работать из чистого клона.
- Коммитьте `uv.lock`; CI ставит окружение через `uv sync --locked`; перед открытием PR запускайте `uv lock --check`.
- Никогда не коммитьте секреты и `.env`, сырые данные, веса моделей, файлы больше нескольких десятков МБ, сгенерированные логи. Данные и артефакты живут в MLflow и MinIO или на хранилище кластера; README говорит, как их получить. GitHub предупреждает на 50 МБ и блокирует файл на 100 МБ.
- Конфигурация живёт в переменных окружения: `.env` локально и в игноре; `.env.example` закоммичен с каждым ключом, заглушкой и комментарием в одну строку; загрузка через python-dotenv или типизированный класс настроек, который падает сразу при отсутствии ключа.
- Хуки pre-commit с первого дня: gitleaks и detect-private-key против секретов, check-added-large-files против данных, плюс `make check`. Каждый клон запускает `pre-commit install`; README говорит об этом.
- Ключ, попавший в историю, скомпрометирован: сначала ротируйте его, затем решите с руководителем, переписывать ли историю. Удаление файла новым коммитом ничего не убирает.
- Один seed читается из окружения, применяется к `random`, NumPy и фреймворку, логируется как параметр запуска. Побитовое совпадение между версиями библиотек и устройствами не гарантировано; seed и lock-файл — то, что вы можете обещать.
- Ноутбуки остаются в `notebooks/`; их выводы могут остаться как отчёт о результате; код, который будет переиспользован, переезжает в `src/`.

## Ветки и коммиты

- Имя ветки: `<тип>/<короткое-описание>` строчными буквами через дефис. Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, плюс `exp` для серии экспериментов. Тот же тип открывает заголовок PR: `feat: ...`.
- Одна ветка на одно изменение; она живёт дни, а не недели. Коммитьте и пушьте в конце каждой рабочей сессии, чтобы история семестра показывала работу, размазанную по неделям.
- Никогда не переписывайте запушенную историю `main`. Мержите PR через squash and merge; заголовок PR тогда становится коммитом в `main`.
- Мелкие правки могут идти в `main` напрямую по договорённости с руководителем; хуки pre-commit срабатывают и на них.
- Формулировки сообщений коммитов необязательны, но полезны: см. [Сообщения коммитов](commit-messages.ru.md).

## Pull request

Вся работа проходит через pull request: он и есть запись того, что сделано и почему. Одна ветка на одно изменение, один PR на ветку.

Поля PR:

- заголовок в стиле ветки: `feat: короткое описание`;
- **План**: три-пять строк руками при открытии PR, что собираетесь сделать;
- **Сделано**: перед снятием Draft сгенерируйте LLM-ассистентом краткое описание проделанной работы по диффу; План и строка `Closes #N` остаются нетронутыми;
- **Как воспроизвести**: что запускает ревьюер, чтобы увидеть результат: команда с её конфигом, откуда берутся данные, запуск MLflow с числами;
- assignee: вы; reviewer: руководитель, его подставит CODEOWNERS при снятии Draft;
- label `enhancement` для новой функциональности;
- Draft, пока работа не готова. Draft нельзя смержить, и он не запрашивает ревью.

Шаблон с этими полями лежит в `.github/pull_request_template.md`, тогда PR никогда не откроется пустым.

Цикл ревью:

1. Руководитель читает и оставляет комментарии одним пакетом.
2. Вы правите отдельными коммитами, без squash и rebase во время ревью, и отвечаете под каждым обсуждением: что изменили и в каком коммите.
3. Повторно запрашиваете ревью кнопкой Re-request review.
4. Обсуждения закрывает руководитель. GitHub позволяет закрыть их и автору, поэтому правило держится на договорённости.

Сроки ответа: по договорённости с руководителем. Пока ждёте, начинайте следующую ветку от текущей; семестр в одном PR копить нельзя.

Несогласие с замечанием: сначала уточните, правильно ли поняли; спорьте фактами и компромиссами, вкус аргументом не считается; предложите два-три варианта; архитектурное решение уходит в ADR.

## Решения

Решения живут в `docs/adr/`, один файл на решение: `NNNN-короткое-название.md`, четырёхзначный сквозной номер, который никогда не переиспользуется, название, которое называет проблему и выбранное решение. Файл следует минимальному шаблону MADR с фронтматтером:

```
---
status: proposed | accepted | rejected | superseded by ADR-NNNN
date: 2026-09-24
decision-makers: <студент>
consulted: <руководитель>
---
# <Проблема и выбранное решение>
## Контекст и постановка проблемы
## Рассмотренные варианты
## Итог решения
### Последствия
## Плюсы и минусы вариантов    <- обязательно, когда отвергнут вариант, предложенный руководителем
```

- Запись пишет ваш LLM-ассистент, никогда не вы руками: в момент решения попросите ассистента составить её по обсуждению, ветке PR и коду, затем проверьте её так же, как проверяете код.
- Что заслуживает записи: структура репозитория и поток данных; библиотека, фреймворк или инструмент вроде трекера, хранилища или LLM-шлюза; интерфейс или контракт данных; бейзлайн, главная метрика, датасет и его разбиение; направление, закрытое отрицательным результатом. Одиночный запуск с другими гиперпараметрами — это запуск MLflow, записи он не требует.
- Запись рождается в ветке фичи со статусом proposed, проходит ревью в PR как код и становится accepted в том же PR до мержа. Отвергнутый вариант мержится с причиной. Принятая запись никогда не правится; изменение — новая запись, которая заменяет старую, со ссылками в обе стороны.
- Запись ссылается на эксперимент или запуск MLflow, который её вызвал.

## Эксперименты и воспроизводимость

- Каждый эксперимент записывается в MLflow. По умолчанию — локальная база: `MLFLOW_TRACKING_URI=sqlite:///mlflow.db` в `.env`, папки `mlruns/` и `mlartifacts/` в игноре. Если `mlflow.db` коммитится, чтобы руководитель открыл его командой `mlflow ui --backend-store-uri sqlite:///mlflow.db`: только один автор, `mlflow gc` перед коммитом, файл меньше 50 МБ, коммит в ветке PR, которая породила запуски, конфликт слияния решается выбором одной стороны и перезапуском. Документация MLflow эту практику не описывает.
- В первую неделю спросите руководителя, есть ли у лаборатории общий tracking server. Если есть, переключите клиент на него: `MLFLOW_TRACKING_URI=https://<сервер>`, `MLFLOW_EXPERIMENT_NAME`, а для S3-совместимого хранилища артефактов `MLFLOW_S3_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` в `.env`; `.env.example` перечисляет их пустыми. Пример лаборатории: сервер и MinIO на кластере.
- Имена: эксперимент `<репозиторий>` или `<репозиторий>/<задача>`; имя запуска `<ветка>-<короткое-описание>`; всегда вызывайте `mlflow.set_experiment`.
- Обязательные теги, согласованные с руководителем один раз: `stage` (baseline, ablation, final), `dataset`, `model_family`, `pr` (номер). Один абзац в заметках запуска.
- Запускайте эксперименты скриптами из чекаута, `uv run python -m <package>.train`, после коммита: MLflow тогда сам записывает коммит. Запуски из ноутбуков тега с коммитом не получают.
- Минимум логирования: `mlflow.autolog()` перед обучением, конфиг как артефакт, итоговая таблица метрик явно.
- Строка результата — коммит, путь к конфигу, seed, id запуска, метрики. Таблица живёт в `results/` или в PR; ВКР ссылается на неё.

## Автоматические проверки

- Одна цель `make check` запускает всё: линт и форматирование ruff, pytest хотя бы с одним smoke-тестом, который прогоняет главный пайплайн на крошечном входе за секунды.
- Три вызывающих, одна цель: pre-commit на вашей машине, CI на каждом PR, хук агента после правок ассистента. Добавьте команду в файл инструкций, который читает ассистент.
- CI на PR добавляет то, что машина проверяет лучше человека: имя ветки и заголовок PR по списку типов, gitleaks, большие файлы, `uv sync --locked`. Задания, которым нужны учётные данные лаборатории, необязательны и пропускаются без секрета.
- Никогда не коммитьте с `--no-verify`; красная проверка чинится.

## Минимальный ожидаемый результат

К каждой контрольной точке покажите руководителю:

1. Репозиторий запускается из чистого клона командами из README.
2. Смерженные PR периода, каждый с Планом, Сделано и Как воспроизвести.
3. Записи в `docs/adr/` по принятым решениям.
4. Запуски MLflow на коммитах этих PR с обязательными тегами.
5. Зелёный CI на `main`; в истории нет секретов и данных.
