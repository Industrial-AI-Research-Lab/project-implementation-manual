# Агентные артефакты — памятка студенту

Агент работает точнее, когда правила проекта записаны в файлах, которые он читает, а проверки запускаются автоматически. Памятка описывает общие файлы инструкций, проверки, overlay и указание использования любого LLM-ассистента. Настройки конкретных продуктов помечены как примеры; выбирать именно этот продукт необязательно. Следуйте памятке, если используете агента в проекте.

## Термины

| Термин | Пояснение | Что это значит для вас |
|---|---|---|
| Агент, harness | Агент — LLM-ассистент, который сам читает файлы, запускает команды и правит код. Harness — среда, в которой он работает: файлы инструкций, разрешения, хуки и проверки. | Чем больше правил записано в harness, тем реже их приходится повторять в запросах. |
| Файл инструкций | Файл, который агент читает при запуске, например AGENTS.md или файл конкретного инструмента. | Храните общие инструкции в AGENTS.md и проверьте, как ваш агент его загружает. |
| Правило (rule), скилл (skill) | Правило — короткая инструкция в отдельном файле, например о стиле кода или о работе с данными. Скилл — набор инструкций для типовой задачи, который агент подключает, когда задача подходит. | Правила и скиллы удобно выносить в overlay и использовать в нескольких проектах. |
| Хук агента | Команда, которую агент запускает на настроенном шаге, например перед окончанием ответа. | Доступность и поведение хуков зависят от агента; сохраняйте также проверки pre-commit и CI. |
| Overlay-репозиторий | Отдельный репозиторий с правилами, скиллами, хуками и настройками агента, который подключают к проекту. Устоявшегося значения у термина нет; в этой памятке он означает именно это. | Наработки по работе с агентами лежат в одном месте и подключаются к любому проекту. |
| Submodule, закрепление версии | Submodule — репозиторий, вложенный в другой на конкретном коммите. Закрепить версию — указать тег или коммит вместо ветки. | Проект не меняется сам, когда меняется overlay: новую версию вы подключаете явно. |
| Доверие к папке (workspace trust) | Вопрос, который агент задаёт при первом открытии папки: доверяете ли вы её содержимому. | Хуки из закоммиченных настроек выполняются с вашими правами; соглашайтесь, только прочитав их. |
| Инъекция промпта | Инструкция для агента, спрятанная в файле или странице, которые он читает. Агент может выполнить её как ваше указание. | Чужие правила и хуки читайте до подключения. |
| Запрет в настройках (permissions deny) | Правило в настройках агента, которое запрещает ему действие, например чтение файла. | Запрет на чтение `.env` не даёт агенту увидеть ваши ключи. |
| Лицензия MIT | Короткая свободная лицензия: код и тексты можно брать, менять и распространять, сохранив текст лицензии. | Без лицензии чужие правила юридически может использовать только их автор. |

## Файлы инструкций

- AGENTS.md в корне репозитория — главный файл. В нём перечислите команды установки и запуска, команду проверки `make check`, соглашения о ветках и PR (см. [памятку о репозитории](../repository/student.ru.md#pull-request)) и правило «никогда не коммитить с `--no-verify`». Держите его коротким, до 200 строк; то, что видно из кода, в него не пишите.
- Пример для инструмента Claude Code: если вы его используете, создайте CLAUDE.md с первой строкой `@AGENTS.md` и допишите ниже только то, что касается Claude Code. Без этой строки Claude Code не прочитает AGENTS.md, если рядом лежит CLAUDE.md.

Примеры файлов инструкций для разных инструментов (при настройке своего агента сверяйтесь с документацией по ссылкам):

| Агент | Файлы инструкций |
|---|---|
| Claude Code | CLAUDE.md, `.claude/rules/`, `.claude/skills/`; AGENTS.md — если нет ни CLAUDE.md, ни CLAUDE.local.md, иначе через импорт `@AGENTS.md` |
| Codex | AGENTS.md |
| Cursor | AGENTS.md, `.cursor/rules/` |
| GitHub Copilot | AGENTS.md, CLAUDE.md, `.github/copilot-instructions.md` |

Выберите файл инструкций, который поддерживает ваш агент, и проверьте, что он загружает правила проекта. У каждого инструмента свои настройки хуков; ниже приведён пример для Claude Code. Общая команда `make check`, настройки pre-commit и CI подходят и для других агентов.

## Что коммитить

Общие файлы кладите в репозиторий проекта или в overlay:

- AGENTS.md и файл конкретного инструмента, если он нужен для загрузки общих инструкций;
- правила и скиллы в папках, которые поддерживает ваш агент;
- общие настройки и скрипты хуков, проверенные командой;
- планы, которые команда ведёт вместе; личное состояние инструментов храните локально.

Пример для Claude Code: CLAUDE.md, `.claude/rules/`, `.claude/skills/`, `.claude/settings.json` и `.claude/check-stop.sh`.

Личные файлы добавьте в `.gitignore`:

```gitignore
# личные настройки агентов
*.local.*
```

Личный CLAUDE.local.md сам по себе отключает чтение AGENTS.md в Claude Code. Если в проекте нет CLAUDE.md, добавьте в CLAUDE.local.md строку `@AGENTS.md`.

Перед коммитом проверьте, что в общих файлах нет токенов и абсолютных путей к вашей машине. Ключи поймает gitleaks из pre-commit, пути ищите сами.

## Одна проверка для агента, pre-commit и CI

Цель `make check` из [памятки о репозитории](../repository/student.ru.md#автоматические-проверки) запускается из трёх мест: хук агента, pre-commit и CI. Правки агента, ваши коммиты и PR проходят одни и те же проверки.

**Настройки агента — пример для Claude Code**, `.claude/settings.json`:

```json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.local)"]
  },
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "bash .claude/check-stop.sh" }
        ]
      }
    ]
  }
}
```

В этом примере Stop запускается перед окончанием ответа. Код выхода 2 просит агента продолжить и передаёт ему вывод проверки. Поле входа `stop_hook_active` равно true, если ход уже продолжился из-за Stop-хука; скрипт ниже повторяет проверки, но второй раз не блокирует завершение. Если проверки снова упали, хук показывает студенту предупреждение; студент должен устранить ошибку. По умолчанию инструмент ограничивает число последовательных продолжений восемью; счётчик сбрасывается после вызова инструмента, поэтому это не предел всех попыток за ход (см. [описание входа Stop](https://code.claude.com/docs/en/hooks#stop-input), проверено 5 октября 2026 года). Хук не гарантирует успешные проверки; итоговую проверку выполняет CI.

Сохраните следующий скрипт в `.claude/check-stop.sh`. Для него нужны Bash и `jq`; при чистом рабочем дереве проверка пропускается:

```bash
#!/usr/bin/env bash
input=$(cat)
[ -z "$(git status --porcelain)" ] && exit 0
if make check >&2; then
    exit 0
fi
if [ "$(printf '%s' "$input" | jq -r '.stop_hook_active // false')" = true ]; then
    printf '%s\n' '{"systemMessage":"Checks still fail after continuation; review the check output before committing."}'
    exit 0
fi
exit 2
```

Полный `make check` после каждого ответа становится медленным, когда тесты идут минутами. Есть два более дешёвых варианта: оставить в хуке Stop только быстрые цели (форматирование, линтер), а тесты доверить pre-commit и CI; или прогонять линтер по отредактированному файлу из хука `PostToolUse` с matcher `Edit|Write`, а полную проверку оставить на Stop. В обоих вариантах сохраните проверку чистого дерева и обработку повторного продолжения из скрипта.

**Pre-commit**, `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: local
    hooks:
      - id: make-check
        name: make check
        entry: make check
        language: unsupported
        pass_filenames: false
```

Значение `unsupported` появилось в pre-commit 4.4; в более старых версиях пишите `system`.

**CI**, `.github/workflows/check.yml`:

```yaml
name: check
on: pull_request
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
      - run: uv sync --locked
      - run: make check
```

**AGENTS.md**:

```markdown
## Проверки
Перед тем как закончить задачу, запусти `make check` и добейся, чтобы он прошёл. Никогда не коммить с `--no-verify`.
```

## Overlay-репозиторий

Общие правила, скиллы и хуки удобно держать в одном overlay-репозитории: исправленное там правило попадёт во все проекты, куда подключён overlay, как только вы обновите в них версию.

Стартовый overlay лаборатории — [nir-agent-overlay](https://github.com/Industrial-AI-Research-Lab/nir-agent-overlay): общие указания, шесть правил и скиллы для записей решений, issue об экспериментах, записей встреч и описаний PR. [Шаблон проекта](https://github.com/Industrial-AI-Research-Lab/nir-project-template) подключает его командой `make overlay`.

**Подключение — пример для Claude Code.** Для другого агента используйте поддерживаемый им способ загрузки инструкций и папку правил. Добавьте overlay в проект как submodule, закрепите версию и создайте символическую ссылку на правила в папке, которую читает агент:

```bash
git submodule add https://github.com/Industrial-AI-Research-Lab/nir-agent-overlay.git .agents/overlay
git -C .agents/overlay checkout v0.1.0
mkdir -p .claude/rules
ln -s ../../.agents/overlay/rules .claude/rules/overlay
git add .gitmodules .agents/overlay .claude/rules/overlay
git commit -m "chore: connect agent overlay v0.1.0"
```

- Общие указания из overlay подключите в CLAUDE.md строкой `@.agents/overlay/AGENTS.md`.
- Ссылка коммитится как символическая. Клон на Windows получит её только при `core.symlinks=true` и праве создавать символические ссылки (режим разработчика); иначе на её месте окажется текстовый файл с путём. Если кто-то в проекте работает на Windows, обойдитесь без ссылки и подключите правила в CLAUDE.md пофайлово: `@.agents/overlay/rules/<имя>.md`.
- Клонируйте проект с флагом `--recurse-submodules`, иначе папка overlay окажется пустой. Напишите об этом в README: руководитель клонирует проект так же.
- Новую версию overlay подключайте через PR: переключите submodule на новый тег и закоммитьте это в ветке `chore/...`. Так в истории видно, когда поменялись правила агента.

**Обмен.** Предложите своей учебной группе завести один общий overlay или объединитесь в меньшие группы с «дружескими» overlay и помогайте друг другу. Дайте однокурсникам ссылку на эту памятку, чтобы все подключали overlay одинаково. Изменения в общий overlay вносите через PR: так остальные видят, что поменялось.

**Лицензия.** Положите в корень overlay файл LICENSE с лицензией MIT. Без лицензии правила юридически может использовать только их автор.

## Чужой overlay: проверка перед подключением

- Прочитайте все хуки, правила и файлы настроек. Хуки выполняются с вашими правами, а правила агент исполняет как ваши указания.
- Смотрите исходный текст файлов, а не только их отображение на GitHub: в HTML-комментариях и невидимых символах бывают инструкции, которые агент прочитает, а вы не заметите.
- Подключайте overlay на теге или коммите; при подключении на ветке чужое изменение попадёт к вам без проверки.
- Запретите агенту читать `.env`, как в примере настроек выше.
- Не кладите в overlay секреты, токены и внутренние адреса: overlay видят все, кто его подключает.

## Как указать, что вы работали с агентами

Добавьте в README проекта раздел «LLM-ассистенты»: какими агентами вы пользуетесь и для чего, ссылки на AGENTS.md и overlay. За код, написанный с агентом, отвечаете вы, как сказано в [общих требованиях](../../general/student.ru.md#использование-генеративного-ии). В статье или ВКР опишите использование так, как требует издатель или программа: IEEE, ACM и Elsevier требуют указывать, что использовался генеративный ИИ, а IEEE прямо относит это требование и к коду.

## Минимальный ожидаемый результат

К контрольной точке покажите руководителю:

1. AGENTS.md в корне с командой `make check`, который загружает ваш агент; файл инструкций конкретного инструмента подключает или повторяет эти общие правила.
2. Общие артефакты агента в репозитории, личные — в `.gitignore`.
3. `make check`, который запускается из хука агента, pre-commit и CI.
4. Раздел «LLM-ассистенты» в README.
5. Если вы подключили overlay: submodule, закреплённый на теге или коммите, и файл LICENSE в корне overlay.
