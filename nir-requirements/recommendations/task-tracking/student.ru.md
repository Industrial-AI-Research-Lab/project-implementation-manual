# Трекинг задач — памятка студенту

Доска задач ведётся там же, где код, и показывает руководителю, как идёт работа, без отдельных сообщений о статусе. Заведите её в первую неделю семестра и ведите до защиты.

## Термины

| Термин | Пояснение | Что это значит для вас |
|---|---|---|
| Доска (GitHub Project), карточка | Доска — проект в GitHub Projects: таблица и канбан-доска из issues, PR и черновиков. Каждая строка доски — карточка. Слово «проект» в этой памятке означает только доску, а не вашу НИР. | Одна доска на семестр, в том же аккаунте, что и репозиторий. |
| Draft issue | Черновик карточки, который есть только на доске: у него нет репозитория, меток и номера. | Годится для быстрой заметки. Перед началом работы превратите черновик в issue (Convert to issue), иначе PR его не закроет. |
| Представление (view) | Сохранённый вид доски: раскладка (доска, таблица, дорожная карта), фильтр и группировка. | Руководитель открывает готовые представления и не настраивает фильтры сам. |
| Встроенная автоматизация (workflow) | Правило доски, которое срабатывает само: например, при закрытии issue или мерже PR карточка переходит в Done. | В первую неделю проверьте, что правила включены, и не двигайте такие карточки руками. |
| Sub-issue | Issue, вложенный в другой issue. Родитель показывает, сколько вложенных задач закрыто. | Родитель — контрольная точка, вложенные issues — эксперименты и задачи к ней. |
| Issue form | Шаблон issue в виде формы с полями, файл в `.github/ISSUE_TEMPLATE/`. | Заводите все эксперименты по одной и той же форме: так гипотеза и итог не потеряются. |
| Критерий готовности (Definition of Done) | Условие, при котором карточку можно перевести в Done. | Здесь: результат уже есть и привязан к карточке. «Я над этим работал» результатом не считается. |
| Причина закрытия: completed, not planned | При закрытии issue GitHub спрашивает причину: сделано (completed) или больше не планируется (not planned). | Эксперимент с отрицательным результатом закрывайте как completed: это тоже результат. Not planned — только для работы, брошенной до результата. |
| Доказательная цепочка, поле «Шаг» | Логика сильного проекта из [общих требований](../../general/student.ru.md#главный-принцип): задача, актуальность, аналоги, gap, вклад, метод, эксперимент, метрики, сравнение, анализ, вывод. Поле «Шаг» отмечает, какое звено закрывает карточка. | По полю видно, какие звенья пока пустые. Если звено пустое, действует формальное ограничение оценки. |
| Ключевое слово закрытия | Строка вида `Closes #N` в описании PR: после мержа в основную ветку issue закрывается сам. | Как им пользоваться, описано в [памятке о репозитории](../repository/student.ru.md#pull-request). |

## Доска в первую неделю

1. Попросите руководителя предоставить доступ Read к приватной стартовой доске лаборатории. Откройте [пустую стартовую доску](https://github.com/orgs/Industrial-AI-Research-Lab/projects/3) → меню проекта → Make a copy. Выберите аккаунт владельца вашего репозитория и задайте название проекта. В доске настроены поля и представления из следующего раздела; задач и черновиков issues нет. Можно также создать доску с нуля по этим настройкам.
2. В репозитории откройте Projects → Link a project и выберите копию. При создании репозитория из шаблона кода доска задач не создаётся. Вкладка Projects показывает доски владельца репозитория.
3. В Settings → Manage access доски пригласите руководителя с ролью Admin. Отдельно пригласите его в участники репозитория.
4. Задайте видимость в Settings → Danger zone. Доски промышленных проектов и проектов под NDA держите приватными; данные партнёра, скриншоты и логи в карточки не выкладывайте.
5. В Settings → Iteration добавьте периоды по две недели на свой семестр и перерывы на сессию. Даты в стартовой доске не заданы. В настройках представления Plan выберите Iteration как поле дат и включите вехи.
6. В Workflows включите Item closed и Pull request merged, задав Status = Done. Настройте Auto-add to project для своего репозитория с фильтром `is:issue is:open`, сохраните и включите правило. Автодобавление и участники не копируются. Существующие issues добавьте вручную через их поле Projects.
7. Составьте задачи вместе с руководителем и назначьте им итерации. Board показывает только текущую итерацию; задачи без итерации там не появятся. Проверьте, что новый issue добавляется автоматически и появляется в Board после назначения текущей итерации.

## Поля и представления

| Поле | Значения | Зачем |
|---|---|---|
| Status | Backlog, In Progress, Blocked, Review, Done | Где карточка сейчас. Blocked — карточка ждёт руководителя, данных или задачи на кластере. Review — по карточке открыт PR. |
| Iteration | итерации по две недели, перерыв на сессию | Как часто вы планируете работу и пишете отчёты. |
| Kind | эксперимент, код, чтение, текст | Тип работы. Типы issue (issue types) в личных репозиториях недоступны, поэтому тип хранится в поле. |
| Шаг | задача и актуальность; аналоги и gap; метод и реализация; эксперимент и метрики; анализ и выводы | Звено доказательной цепочки. Пять групп — сокращённый вариант цепочки из общих требований и [шаблона задач](../../llm-assistant/project-context.ru.md#задачи). |
| Target date | дата | Срок карточки. |

Представления:

- **Доска**: раскладка Board по Status, фильтр `iteration:@current`.
- **План**: раскладка Roadmap по итерациям, с вехами.
- **Просрочено**: таблица с фильтром `iteration:<@current is:open`, то есть открытые карточки прошлых итераций.

## Карточки и готовность

- Карточка — один шаг, который заканчивается PR или письменным итогом в описании issue. Если карточка неделю не выходит из In Progress, разбейте её.
- Ограничения на число карточек в работе нет. Держите в In Progress две-три карточки: так их проще довести до конца. Всё, что ждёт других, переносите в Blocked.
- Карточка переходит в Done, когда у неё есть результат и он привязан к карточке:
  - смерженный PR с `Closes #N`;
  - запись в [журнале чтения](../papers/student.ru.md#чтение-и-заметки) для карточки «чтение»;
  - итог и интерпретация в описании issue эксперимента;
  - раздел текста в репозитории для карточки «текст».

## Эксперименты как issues

- Заведите родительский issue на каждую контрольную точку и вложите в него sub-issues: один эксперимент — один issue.
- Эксперименты заводите по форме `.github/ISSUE_TEMPLATE/experiment.yml`. Создание пустых issues отключите строкой `blank_issues_enabled: false` в `.github/ISSUE_TEMPLATE/config.yml`. Обязательность полей формы GitHub проверяет только в публичных репозиториях.

```yaml
name: Эксперимент
description: Одна гипотеза — один issue
title: "exp: "
projects: ["<владелец>/<номер доски>"]
body:
  - type: textarea
    id: hypothesis
    attributes:
      label: Гипотеза
    validations:
      required: true
  - type: textarea
    id: setup
    attributes:
      label: Постановка
      description: Данные, бейзлайн, метрика
  - type: textarea
    id: expected
    attributes:
      label: Ожидаемый результат
  - type: textarea
    id: result
    attributes:
      label: Итог и интерпретация
      description: Заполняется при закрытии
```

- Номер issue указывайте в описании PR (`Closes #N`) и в заметке запуска MLflow: тогда результат, код и обсуждение будут связаны между собой.
- Отрицательный результат закрывайте как completed и описывайте в issue итог и то, что он значит для работы. Как not planned закрывайте только работу, брошенную до результата.
- Если результат ломает дальнейший план, попросите LLM-ассистента составить ADR с новым планом, обсудите его с руководителем и обновите карточки и вехи.

## План семестра

1. Сначала внесите даты, которые от вас не зависят: сдача отчёта, предзащита, проверка на заимствования, защита. Три контрольные точки из [памятки руководителю](../../general/supervisor.ru.md#контрольные-точки-руководителя) — начало проекта, до середины, перед защитой — оформите вехами (milestones) репозитория: у каждой вехи укажите дату, а в описании перечислите ожидаемые артефакты. Точные даты уточняйте в расписании своей программы.
2. Разбейте семестр на итерации по две недели с перерывом на сессию. Весь семестр планируйте до уровня итераций, ближайшую итерацию — до уровня карточек: подробный план на месяц вперёд ломается при первой неожиданности.
3. Основной объём работы планируйте так, чтобы он помещался примерно в половину семестра. Новые идеи, модели и датасеты кладите в Backlog; в план они попадают только после письменного согласия руководителя в issue.
4. В конце итерации перенесите незаконченные карточки в следующую (Move items to…) и напишите в отчёте, почему они не закрыты.

## Отчёты и встречи

**Отчёт на доске.** Как часто писать отчёт, обсудите с руководителем в начале семестра; минимум — раз в итерацию. Отправляйте отчёт, даже если руководитель его не просил и результатов пока нет: по нему видно, где работа застряла. Пишите его как status update на доске: выберите статус On track, At risk или Off track и заполните три пункта:

- что сделано по сравнению с прошлым планом, со ссылками на закрытые issues и PR;
- план на следующую итерацию: пункты, выполнение которых можно проверить;
- что вам нужно от руководителя: решение, совет или отзыв.

**Встречи.** Например, в нашей лаборатории встречи проходят в Толке (itmo.ktalk.ru). Не забудьте включить запись в начале встречи, а лучше запланируйте встречу заранее и включите автозапись при планировании: тогда запись начнётся сама. Предупредите участников, что встреча записывается. После встречи Толк сделает расшифровку с именами говорящих и таймкодами, а также резюме встречи; они появятся в разделе «Артефакты → Видеозаписи → Обзор».

1. Попросите LLM-ассистента составить по резюме файл `docs/meetings/YYYY-MM-DD.md`: участники по ролям, ссылка на запись, решения с таймкодами, задачи с ответственным, ссылкой на issue и сроком, открытые вопросы, дата следующей встречи.
2. Сверьте решения, числа и имена с расшифровкой: если нажать на реплику, Толк воспроизведёт этот фрагмент записи. Резюме составляет нейросеть, и в нём бывают ошибки.
3. Записи ADR и задачи Толк не создаёт, это ваша работа: попросите ассистента составить по файлу встречи запись ADR (см. [памятку о репозитории](../repository/student.ru.md#решения)), а задачи со встречи оформить как issues и добавить на доску через `gh`. Один раз разрешите `gh` работать с досками: `gh auth refresh -s project`.

   ```bash
   gh issue create --title "..." --body "..." --project "<название доски>"
   ```

4. Добавьте файл встречи через PR: руководитель подтвердит запись, одобрив PR. В репозиторий кладите только резюме. Полную расшифровку можно добавить только после санитизации, то есть очистки от персональных и конфиденциальных данных; как её провести, чем расшифровать запись без Толка и какие промпты использовать, описано в [справке о записях встреч](meeting-records.ru.md).

**Отставание.** Если вы отстаёте, сразу ставьте статус At risk, не дожидаясь контрольной точки. Договоритесь с руководителем, к какой дате проблема должна быть решена и по какому признаку вы это поймёте. Если отставание сохраняется, запишите новый план: ADR и новые даты вех.

**Руководитель не открывает доску.** Отправьте ссылку на отчёт с тремя пунктами туда, куда договорились с руководителем: чаще всего это Telegram или почта. В сообщении только ссылка, а сами сведения остаются на доске.

## Конец семестра

- Закройте все карточки: готовые — через PR или итог в issue, остальные — как not planned с причиной.
- Напишите финальный отчёт на доске со ссылками на отчёт по практике, релиз и записи ADR.
- Отправьте карточки из Done в архив (Archive): значения полей сохраняются, архивацию можно отменить.
- Список выполненной работы для отчёта по практике соберите из закрытых issues каждой вехи. Формальные документы по-прежнему сдаются через университет.

## Минимальный ожидаемый результат

К каждой контрольной точке покажите руководителю:

1. Доску с полями Status, Iteration, Kind, «Шаг» и тремя представлениями; руководитель в ней — Admin.
2. Отчёт на доске за каждую итерацию периода.
3. Issue на каждый эксперимент периода с итогом и интерпретацией.
4. Файлы встреч в `docs/meetings/` со ссылками на issues и ADR.
5. Вехи с датами и актуальным процентом выполнения.
