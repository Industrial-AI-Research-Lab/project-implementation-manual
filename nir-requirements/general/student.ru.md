# Общие требования к НИР/проекту — памятка студенту

## Главный принцип

Проект оценивается не по факту «что-то сделано», а по тому, насколько убедительно доказаны качество, самостоятельность и полезность результата.

Базовая логика сильного проекта:

**задача → актуальность → существующие решения → gap/ограничение → собственный вклад → метод/реализация → эксперимент или практическая проверка → метрики → сравнение → анализ → вывод.**

Для сложной многокомпонентной системы дополнительно:

**система → компоненты → вклад каждого компонента → ablation/анализ компонентов → сравнение с аналогами → итоговый эффект.**

## Что должно быть в любом сильном проекте

- Актуальность не просто заявлена, а доказана через научный, технологический или индустриальный контекст.
- Постановка конкретна: понятны входы, выходы, ограничения и критерии успеха.
- Проанализированы релевантные аналоги, бейзлайны и/или SOTA.
- Есть собственный содержательный результат, а не только запуск готового решения.
- Есть количественная проверка по обоснованным метрикам.
- Сравнение проводится в одинаковых или сопоставимых условиях.
- Результаты не только показаны, но и интерпретированы: почему так получилось, где решение сильнее/слабее, каковы ограничения.
- Результат воспроизводим другим исследователем/разработчиком.
- Все обязательные артефакты проекта реально содержательны, а не существуют формально.
- На защите студент способен самостоятельно объяснить постановку, метод, архитектуру, метрики, бейзлайны, результаты и ограничения.

## Что критично для оценки 5А

Для 5А одновременно нужны:

1. все обязательные артефакты своего типа проекта;
2. количественное сравнение с релевантными существующими решениями;
3. воспроизводимость;
4. самостоятельное понимание собственной работы;
5. выполнение специальных требований выбранного типа проекта.

Итоговая оценка не является средним арифметическим. Один критический провал может ограничить максимальную оценку.

### Формальные ограничения

- нет всех обязательных артефактов → максимум **4В**;
- нет количественного сравнения с аналогами → максимум **4С**;
- нет ни одного содержательного бейзлайна/аналога → максимум **3D**;
- для сложной системы нет анализа вклада компонентов → максимум **4С**;
- студент не может объяснить существенную часть работы → максимум **3D**;
- не доказана актуальность → максимум **4С**;
- нет работающего/проверяемого результата → максимум **3E**, а при отсутствии содержательного результата — **2FX**;
- репозиторий не позволяет проверить результат → максимум **4С**;
- презентация не позволяет понять постановку, метод и результаты → максимум **4С**;
- студент не отвечает на базовые вопросы → максимум **3D**.

## Репозиторий и воспроизводимость

Для программных проектов репозиторий — отдельный объект оценки. На высоком уровне ожидаются:

- понятная структура;
- содержательный README с постановкой задачи;
- инструкции по установке и запуску;
- зафиксированные зависимости и конфигурации;
- возможность воспроизвести основные эксперименты/результаты;
- тесты там, где они нужны;
- модульный и читаемый код;
- организованные результаты экспериментов;
- документация архитектуры для сложной системы;
- отсутствие секретов и API-ключей;
- история коммитов в течение семестра, демонстрирующая реальную работу над проектом.

## Презентация и защита

Сильная презентация быстро показывает:

**проблема → актуальность → аналоги → gap → собственный вклад → метод/архитектура → эксперимент → количественные результаты → сравнение → ограничения → выводы.**

На защите важно не читать слайды, а самостоятельно объяснять решения и отвечать на вопросы, включая причины полученных результатов и ограничения.

## Артефакты

Конкретный набор зависит от типа проекта. Минимально почти всегда нужна презентация; для научного и технологического проектов — также содержательный текстовый артефакт и открытый репозиторий; для индустриального — рецензия индустриального представителя; для коллаборативного — оценка командного вклада.

Формальная ссылка не считается выполнением требования: содержание артефакта должно позволять проверить заявленный результат.

## Организационные положения

Проект рассматривается как завершённая работа на семестр; студент формирует портфолио из нескольких законченных проектов и может продолжить тему у того же руководителя. В конце проекта представляются презентация и дополнительные артефакты соответствующего типа.

При защите учитываются не только обязательные результаты, но и дополнительные достижения: публикации, патенты, акты о внедрении, качественные технологические статьи, популярность открытого ПО и т. п.

## Использование генеративного ИИ

Генеративный ИИ разрешён, кроме фальсификации результатов. За ошибки, внесённые с помощью ИИ, студент отвечает так же, как за собственные. Удачное и содержательное применение ИИ может рассматриваться как дополнительное достижение.
